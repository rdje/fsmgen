# OSVVM Runtime Execution and Measurement

The exact OSVVM runtime path separates structural planning from external tool
execution. Child `.17.3.7.1` first materializes the authored portable-VHDL
reference, gate, and qualification sources through the qualified OSVVM
wrapper. Child `.17.3.7.2` then binds those graphs to the exact provider,
tool, source order, commands, reports, and resource controls needed by the
qualified GHDL route. Neither step starts GHDL.
Children `.17.3.7.3` and `.17.3.7.4` then execute and measure that authority,
and `.17.3.7.5` now closes the chain with one clean guarded immutable capture
plus an independent fresh-process reload. This chapter makes no promoted
performance, capacity, support, or provider-generality claim.

## Reproduction and use

t1677 independently reconstructs and validates all three exact plans. Its
hostile controls cover command mutation, preflight admission, unknown input,
direct private-seam access, and subclass widening:

```bash
prove -Iperl \
  t/1677-vial-architecture-scale-osvvm-runtime-execution-plan.t
```

Internal orchestration can inspect a gate plan without creating its
content-addressed stage or starting GHDL:

```perl
use FSM::VIAL::ArchitectureScaleOSVVMRuntimeExecutionPlan;

my $plan =
    FSM::VIAL::ArchitectureScaleOSVVMRuntimeExecutionPlan->evaluate({
        repository_root => '.',
        level => 'gate_candidate_v1',
    });

die "unexpected execution"
    if $plan->{claims}{staging_created}
        || $plan->{claims}{external_tool_executed};
```

## Provider-aware lifecycle execution

The shared GHDL lifecycle now has a distinct caller-sealed OSVVM authority.
Portable qualification and measurement retain their original lifecycle
schema, request shape, state bytes, command family, storage policy, and result
projection. The OSVVM qualifier alone receives the versioned multi-command
authority; an ordinary caller, subclass, or portable role cannot acquire it.

The provider-aware role prepares the generated OSVVM settings, the `osvvm`,
`osvvm_common`, and `fsmgen_vial` libraries, and the supplementary-report
directory beneath one content-addressed repository-volume stage. It then uses
the same production process supervisor and forward-only state chain for:

| Lifecycle state | Sealed OSVVM work |
| --- | --- |
| `tool_verified` | exact qualified GHDL version |
| `analyzed` | every provider command in order, then generated sources and probe |
| `elaborated` | separate fixture and provider-probe commands |
| `ran` | separate fixture and provider-probe executions and report snapshots |
| `trace_validated` | portable trace-v2 validation from fixture output only |
| `result_produced` | portable normalized-result validation from fixture output only |
| `assembled` / `cleaned` | sealed private evidence followed by exact owned removal |

Every command has its own supervisor capture. Resumption revalidates the GHDL
archive and binary, the complete ordered repository source set, generated
settings, predecessor states, content objects, and work libraries. Provider
reports are copied into sealed objects after each probe execution and removed
from the raw report directory before the next state. They remain supplementary
evidence and cannot replace portable trace or normalized-result truth.

The checked qualifier no longer has a second process implementation. It
reconstructs the private execution plan, admits that plan to the lifecycle,
advances every state, and builds the existing public report from the cleaned
assembly. Live qualification still reproduces the checked report byte-for-byte;
the checked portable qualifier is also unchanged. Hostile controls cover
alternate resource policy, generated-settings mutation, absent reports,
caller widening, state/object/source/provider mutation, collision, process
failure, and cleanup. On Darwin, the watcher explicitly applies an ad-hoc
signature to its freshly compiled repository-local fake GHDL executable before
testing this path; that prevents external-volume linker-signature stalls and
does not modify or substitute the pinned production GHDL binary.

## Common-controller measurement

`ArchitectureScaleOSVVMRuntimeMeasurement` now maps the exact plan and
provider-aware lifecycle onto the fixed common-controller stages. Construct,
parse/validate, bridge, and bind-plan rebuild the ordinary authored VIAL route.
Emit performs callback-scoped provider verification, emits the qualified
OSVVM wrapper graph, materializes the seven generated sources in canonical
plan order, and admits a relocated 68-source lifecycle request. The three
external controller stages retain every provider/generated analysis capture,
both elaboration captures, and separate fixture/provider-probe captures.
Trace and normalized-result truth still come only from the portable fixture.

Each executable role uses one lifecycle execution per controller record. The
reference role has one correctness-only validation. Gate has one validation
and three independently measured records; qualification has one validation
and five independently measured records. Each record executes the fixture
once and the provider probe once, snapshots four supplementary provider
reports, verifies provider identity again after execution, publishes bounded
identity/report evidence, and removes both the lifecycle and outer controller
roots. The single executions deliberately make no intra-record deterministic-
rerun claim; independence comes from the controller's separate records.

The guarded exact watcher accepts all eleven records with no exclusions or
residue. Validated trace counts are exactly 77 for reference, 10,000 for every
gate record, and 100,000 for every qualification record. Every record retains
61 provider-analysis captures, one generated-analysis capture, two elaboration
captures, one fixture capture, one provider-probe capture, four reports, 68
source identities, the complete lifecycle predecessor chain, and stable
pre/post OSVVM commit/tree/manifest authority.

Limit and over-limit stop at materialization preflight: they acquire no plan,
provider callback, common controller, lifecycle, or external tool. This work
publishes measurement evidence only. It does not promote a performance budget,
product-support statement, capacity boundary, provider-generality,
mixed-language, or public-API claim.

## Immutable publication implementation

`ArchitectureScaleOSVVMRuntimeMeasurementMatrix` is a separate exact-class
publisher. It cannot inherit the portable-VHDL matrix or share that matrix's
schemas, profile identities, staging namespace, or aggregate identities. Its
five-role order comes directly from the OSVVM measurement producer:

| Role | Publisher route |
| --- | --- |
| reference | correctness-only validation |
| gate candidate | validation plus three measured records |
| qualification candidate | validation plus five measured records |
| limit | preflight-dominated, inheriting the executable capture identity |
| over-limit | preflight-dominated, inheriting the executable capture identity |

Each role executes or reloads in its own child. The child first validates and
atomically publishes the complete canonical report in its content-addressed
profile directory. Only a separately bounded compact manifest entry crosses
the coordinator pipe. Thus the long-lived coordinator neither transports nor
retains the raw provider, command, transcript, report, trace, result, sample,
and cleanup evidence through its IPC envelope.

All five entries must bind one clean Git revision, host profile, exact pinned
OSVVM/GHDL tool profile, and active resource guard. Tool-free limit and excess
reports may inherit that tuple only after executable evidence establishes it;
they cannot originate or change it. Family and complete manifests appear only
after ordered reload validates every report, artifact digest and size, sample
count, dominance count, nonclaim, and common identity. Conflicting immutable
targets, incomplete or reordered profiles, mixed or stale identity, repeated
samples, child failure or signal, oversized report/IPC, unsafe paths, symlinks,
and malformed or ambiguous crash staging fail closed. Byte-exact abandoned
staging alone may be recovered. The conservative 67,108,864-byte publication
ceiling reuses an existing GHDL runtime-capture authority; it is containment,
not a performance or capacity claim.

Inspect the immutable inventory without starting provider or tool work:

```console
scripts/run_vial_osvvm_runtime_measurement_matrix.pl --inventory
```

After this implementation is committed cleanly, exact capture and independent
reload run as separate guarded processes:

```console
scripts/run_with_ram_guard.sh -- \
  scripts/run_vial_osvvm_runtime_measurement_matrix.pl
scripts/run_with_ram_guard.sh -- \
  scripts/run_vial_osvvm_runtime_measurement_matrix.pl --validate
```

The default `t/1680-vial-architecture-scale-osvvm-runtime-measurement-matrix.t`
checks producer ownership, routing, guard enforcement, child isolation,
canonical bounded IPC, immutable publication/recovery, collision and ambiguity,
preflight identity inheritance, aggregate drift, raw-evidence expectations,
runner isolation, and cleanup without launching the exact campaign. No
immutable OSVVM measurement set was claimed until the clean guarded capture
and distinct fresh-process reload both passed.
