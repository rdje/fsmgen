## Shipped Public Syntax

The behavior is enabled only by the explicit burst-last read response-demux
arm:

```text
(response-demux
  (read
    (response-event axi0_read_complete)
    (response-scope burst-last)
    (last-signal axi0_rlast (width 1))
    (transaction-completion generated)))
```

The shipped `single-beat` read response-demux behavior remains unchanged.
`read-data` remains single-beat only and is still rejected when paired with
`response-scope burst-last`.

## Generated IAL1 Boundary

For the checked-in burst-last sample, generated IAL1 now contains:

```text
(input axi0_read_complete)
(input axi0_rid (width 4))
(input axi0_rlast)
(output axi0_r0_complete)
(output axi0_r1_complete)
```

`axi0_read_complete` is the raw accepted read response beat input.
`axi0_rid` is the generated response-ID input. `axi0_rlast` is the generated
last-beat marker input. `axi0_r0_complete` and `axi0_r1_complete` are
generated one-cycle pulse outputs, not authored completion inputs.

Each read auto-ID transaction gets one response-demux rule. The rule pulses
only on a raw response beat with an active matching `RID` and asserted
`RLAST`:

```text
(rule axi0_r0_response_demux
  (& axi0_read_complete axi0_r0_auto_id_busy_q
     (== axi0_rid axi0_r0_auto_id_q)
     axi0_rlast)
  (pulse axi0_r0_complete))
```

Matched non-last beats do not pulse the transaction completion output.

## Release And Assertions

Read capacity release and read auto-ID release consume the generated
transaction completion pulses. Under `burst-last`, that means release occurs
on the matched last beat rather than on every matched read response beat.

The generated assertion set keeps the same bounded response-demux checks as
single-beat read demux:

```text
axi0_read_response_demux_active_match
axi0_r0_r1_read_response_demux_unique_match
```

Those assertions are evaluated on accepted read response beats and require the
beat's `RID` to match an active auto-ID transaction, with at most one active
match. Burst length, missing `RLAST`, extra beats after `RLAST`, and `ARLEN`
or beat-count consistency are not claimed or generated by this slice.

behavior:

```text
response_demux:
  mode: bounded_response_demux_contract
  generated_behavior: true
  read:
    mode: bounded_read_rid_demux_contract
    generated_behavior: true
    response_event: axi0_read_complete
    response_event_role: raw_accepted_read_response_beat
    response_scope: burst_last
    response_id_signal: axi0_rid
    response_id_direction: generated_input
    last_signal: axi0_rlast
    last_signal_direction: generated_input
    last_signal_width: 1
    transaction_completion_source: generated_demux_last_beat
    transaction_completion_semantics: matched_rid_and_last_signal
    beat_valid_output: none
    burst_length_source: rlast_only
    burst_length_validation: not_generated
    generated_rules:
      - axi0_r0_response_demux
      - axi0_r1_response_demux
    generated_completion_signals:
      - axi0_r0_complete
      - axi0_r1_complete
    generated_assertions:
      - axi0_read_response_demux_active_match
      - axi0_r0_r1_read_response_demux_unique_match
  residue:
    - read_data_interleaving
    - bursts
```

`auto_id_lifecycle.residue` removes `response_demux` for the sample, and the
read same-ID family reports `response_demux_covered: true`.

beat-count ownership, missing/extra beat validation, per-transaction

direct backend lowering, and VHDL backend/reroute behavior remain future
exact-owner work.
