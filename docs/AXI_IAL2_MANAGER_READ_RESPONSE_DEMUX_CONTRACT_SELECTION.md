## Purpose

This selector chooses the bounded public `.ppif` contract for read `RID`
response demux. The goal is to make the read response scope explicit before
parser/report metadata or generated read demux behavior changes.

## Selected Public Syntax

Extend the existing optional `response-demux` clause under
`manager-capacity-status` with a read family arm:

```text
(response-demux
  (read
    (response-event axi0_read_complete)
    (response-scope single-beat)
    (transaction-completion generated)))
```

The shipped write arm remains valid and may coexist with the read arm:

```text
(response-demux
  (write
    (response-event axi0_write_complete)
    (transaction-completion generated))
  (read
    (response-event axi0_read_complete)
    (response-scope single-beat)
    (transaction-completion generated)))
```

`response-scope single-beat` is mandatory for the first read contract. It
means the named read response event represents one accepted read response
transfer that completes exactly one non-burst/single-beat logical read
transaction. It is not a burst last-beat abstraction, not a read-data
reassembly event, and not an already-demuxed per-transaction completion.

For this bounded slice, `response-event` must equal the existing top-level
`read-complete` event. Under the explicit read demux opt-in, top-level
`read-complete` is interpreted as the raw accepted read response transfer
event for the selected single-beat scope.

`transaction-completion generated` means each opted-in read transaction's
`(completion NAME)` signal is generated by read response demux. Without an
explicit read `response-demux` arm, read transaction completion names remain
authored/environment inputs as they do today.

## Static Contract

The first parser/report implementation must enforce:

- `response-demux` remains optional and may appear at most once under
  `manager-capacity-status`;
- the clause may contain one `(write ...)` arm, one `(read ...)` arm, or both;
- duplicate read or write family arms are rejected;
- `(read ...)` requires exactly one `(response-event EVENT)` clause;
- `(read ...)` requires exactly one `(response-scope single-beat)` clause;
- `(read ...)` requires exactly one `(transaction-completion generated)`
  clause;
- the first read contract rejects any response scope other than `single-beat`;
- `EVENT` must equal top-level `read-complete`;
- read demux requires positive-width read `id-families` metadata with a
  response ID signal;
- read demux requires `transactions` metadata with at least one read
  transaction using `(id auto)`;
- read demux requires explicit read `auto-id-lifecycle` metadata;
- read demux on a zero-width read ID family is rejected;
- read demux with no auto-ID read transactions is rejected;
- response events, transaction completion names, read ID-family signals,
  status outputs, storage names, generated demux names, and generated
  assertion names must remain collision-free.

This selector does not make existing `(id auto)` or read transaction
completion syntax behavior-bearing by itself. The explicit read
`response-demux` arm is required.

## Report Contract

The parser/report metadata slice should keep schema
`fsmgen.ial2.protocol_intent.axi_manager_capacity_status.v1` and add a
machine-readable `read` entry under `response_demux`.

For a read-only metadata slice before generated behavior, the selected report
shape is:

```text
response_demux:
  mode: bounded_response_demux_contract
  generated_behavior: false
  read:
    mode: bounded_read_rid_demux_contract
    generated_behavior: false
    response_event: axi0_read_complete
    response_event_role: raw_accepted_read_response
    response_scope: single_beat
    response_id_signal: axi0_rid
    response_id_direction: generated_input
    transaction_completion_source: generated_demux
    auto_transactions: [r0, r1]
  residue:
    - generated_read_rid_demux
    - read_data_interleaving
    - bursts
```

If a source contains both shipped write demux and the new read arm, the report
must preserve the existing generated write behavior and add
`read.generated_behavior: false` for the read arm until a later behavior owner
ships generated read demux. Per-family `generated_behavior` is mandatory so a
mixed write/read report does not imply generated read demux prematurely.

## Future Behavior Boundary

A later behavior owner may use this contract to:

- declare the read response ID signal (`RID`) as a generated IAL1 input;
- match `response_event && busy && (RID == selected_id)` for each active
  generated auto-ID read transaction;
- pulse the generated read transaction completion signal for the matching
  transaction;
- release the selected read ID from the generated demux match;
- emit unmatched/inactive read response and ambiguous-match assertions.

That future behavior is still single-beat/non-burst only unless another task
owns burst or read-data collection semantics.

## Diagnostics Expected In The Parser/Report Slice

The selected parser/report implementation should reject:

- duplicate `response-demux` clauses;
- duplicate `(read ...)` family arms;
- missing or duplicate `(response-event ...)`;
- missing, duplicate, or unsupported `(response-scope ...)`;
- response scopes other than `single-beat`;
- missing or malformed `(transaction-completion generated)`;
- `response-event` values that differ from top-level `read-complete`;
- read response demux without `id-families`;
- read response demux without `transactions`;
- read response demux without read `auto-id-lifecycle`;
- read response demux on zero-width read IDs;
- read response demux with no auto-ID read transactions;
- any generated signal or assertion name collision.
