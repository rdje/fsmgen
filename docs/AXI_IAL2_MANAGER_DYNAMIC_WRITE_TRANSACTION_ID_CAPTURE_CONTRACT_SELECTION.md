# AXI IAL2 Manager Dynamic Write Transaction-ID Capture Contract Selection

Status: selector for `IAL2-FEATURE-COMPLETENESS-FRONTIER.222` on
2026-06-22.

Current note: later leaves moved selected single-active dynamic read matching,
selected dynamic read-data shapes, and bounded all-dynamic multiple write
response-demux out of the `.222` residue. See the current behavior docs for
those shipped follow-ups.

Task-tree owner: `IAL2-FEATURE-COMPLETENESS-FRONTIER.222`

## Decision

Select `IAL2-FEATURE-COMPLETENESS-FRONTIER.223`, direct generated behavior for
bounded dynamic write transaction-ID capture and `BID` response matching.

The public contract reuses the existing explicit write response-demux clause
with a transaction-local dynamic write ID. No new dynamic-ID lifecycle clause
is selected:

```lisp
(transactions
  (write w0
    (tag wr0)
    (request axi0_w0_request)
    (completion axi0_w0_complete)
    (id dynamic)))

(response-demux
  (write
    (response-event axi0_write_complete)
    (transaction-completion generated)))
```

`(id dynamic)` remains the request-ID source contract. The matching
`response-demux.write` arm is the explicit opt-in that turns that metadata
into generated write response matching. Accepting the same clause as
metadata-only would make `(transaction-completion generated)` misleading, so
the next owner should implement the bounded behavior directly rather than
split out a selected-not-generated response-demux report first.

This selector changes no parser, generator, PPIF sample, support-accounting
catalog, validation, generated artifact, test, or HDL behavior.

## First Supported Boundary

The first generated dynamic write response-demux behavior is intentionally
narrow:

- exactly one write transaction in the selected write family has
  `(id dynamic)`;
- the selected write family has a positive-width `id-families.write` entry
  with request ID source, such as `AWID`, and response ID signal, such as
  `BID`;
- the dynamic write transaction has unique per-transaction request and
  completion events;
- the transaction completion event is generated by `response-demux.write` and
  is distinct from the raw write response event;
- the selected family has no same-family `auto-id-lifecycle.write`,
  `same-id-ordering.write`, concrete same-ID queue-head response-demux, mixed
  auto-ID/queue-head response-demux, or additional write transaction behavior
  in the first generated dynamic slice.

Unrelated read-family dynamic ID metadata may remain metadata-only when no
read-family behavior clause consumes it, but the first support-accounted
behavior sample should keep the shape minimal with one dynamic write
transaction.

## Capture Contract

The generated capture point is the admitted dynamic write request, not the raw
request pulse alone. The capture guard is the transaction request event gated
by the same scalar write capacity acceptance expression used by the admitted
request boundary, and by the single-active dynamic ownership bit:

```text
request_event
&& !dynamic_busy
&& (pending_writes < write_max_pending || write_completion_fanin)
```

The capture action stores the family write request-ID source into a generated
selected-ID register and sets the busy bit:

```text
dynamic_id_q   <= AWID
dynamic_busy_q <= 1
```

The first slice does not support a new dynamic request while that busy bit is
set, including a same-cycle request with a matching response for the previous
dynamic ID. That stricter single-active rule avoids an update-order ambiguity
in the initial generated storage shape. A later owner may select
release-and-recapture semantics after queue/scoreboard rules are explicit.

## Response Matching Contract

The generated write response-demux rule uses the existing response-demux match
shape with dynamic selected-ID storage:

```text
response_event && dynamic_busy_q && (BID == dynamic_id_q)
```

The rule pulses the transaction completion signal selected in the public
transaction record. Dynamic busy release is driven by that generated
completion pulse.

The generated assertions must cover at least:

- an admitted dynamic write request is not accepted while the dynamic write
  transaction is already busy;
- a raw write response event matches an active dynamic write transaction;
- a generated dynamic write completion releases an active dynamic write
  transaction.

The existing unique-match assertion family remains future work because the
first dynamic write contract has exactly one dynamic write transaction.

## Report Vocabulary

The next behavior owner should preserve the existing transaction ID report and
replace only the implementation status for the covered transaction when
behavior is generated:

```yaml
transactions:
  - name: w0
    kind: write
    id:
      policy: dynamic
      request_id_source: axi0_awid
      response_id_signal: axi0_bid
      ownership: user_supplied
      implementation_status: generated_capture_matching
```

The `response_demux.write` report should use a dynamic-specific mode and
artifact vocabulary:

```yaml
response_demux:
  mode: bounded_dynamic_write_bid_demux_contract
  generated_behavior: true
  write:
    response_event_role: raw_accepted_write_response
    response_id_signal: axi0_bid
    transaction_completion_source: generated_dynamic_demux
    transaction_completion_semantics: matched_dynamic_id
    dynamic_transactions:
      - w0
    dynamic_capture:
      request_id_source: axi0_awid
      capture_event_source: admitted_dynamic_write_request
      ownership: single_active_dynamic_write
      selected_id_signal: axi0_w0_dynamic_id_q
      busy_signal: axi0_w0_dynamic_busy_q
      capture_rule: axi0_w0_dynamic_id_capture
      release_rule: axi0_w0_dynamic_id_release
    generated_rules:
      - axi0_w0_response_demux
    generated_completion_signals:
      - axi0_w0_complete
    generated_assertions:
      - axi0_w0_dynamic_request_not_busy
      - axi0_write_dynamic_response_active_match
      - axi0_w0_dynamic_completion_active
```

The existing `dynamic_transaction_id_behavior` residue should narrow only
after behavior ships: dynamic write ID capture and `BID` matching are covered
for the single-active write shape, while dynamic read matching, dynamic
same-ID ordering, read-data routing, queues, scoreboards, mixed dynamic/static
families, multiple dynamic write transactions, same-cycle recapture,
direct-backend behavior, and VHDL remain residue.
