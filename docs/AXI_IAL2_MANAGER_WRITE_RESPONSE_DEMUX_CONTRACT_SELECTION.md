## Purpose

This selector chooses the first public response-demux contract after bounded
auto-ID request-ID drive. The goal is to make the next parser/report slice
reviewable before generated response matching changes behavior.

## Selected Public Syntax

Add an optional `response-demux` clause under the existing
`manager-capacity-status` object:

```text
(response-demux
  (write
    (response-event axi0_write_complete)
    (transaction-completion generated)))
```

This first contract is intentionally write-only. It selects `BID` response
demux for write transactions whose IDs are owned by the explicit
`auto-id-lifecycle` contract. Read `RID` demux remains separate because read
data needs `RVALID/RREADY`, `RLAST`, burst/last-beat ownership, and
interleaving/reassembly policy.

`response-event` names the raw write response accepted event. For the first
bounded contract it must equal the existing top-level `write-complete` event.
That keeps the current capacity/status object shape intact while making the
source explicit that this event is the response-channel accepted pulse used by
demux.

`transaction-completion generated` means each `(transactions (write NAME ...
(completion COMPLETION) ...))` completion name is generated by response demux
for opted-in write transactions. Without `response-demux`, transaction
completion names remain authored/environment inputs exactly as they do today.

## Static Contract

The first parser/report implementation should enforce:

- `response-demux` is optional and may appear at most once under
  `manager-capacity-status`;
- the first supported family subclause is `write` only;
- `(write ...)` requires exactly one `(response-event EVENT)` clause;
- `(write ...)` requires exactly one `(transaction-completion generated)`
  clause;
- `EVENT` must equal the existing top-level `write-complete` event in the first
  bounded slice;
- write demux requires positive-width write `id-families` metadata with a
  response ID signal;
- write demux requires `transactions` metadata with at least one write
  transaction using `(id auto)`;
- write demux requires explicit `auto-id-lifecycle` metadata for `write`;
- transaction completion signal names, response event names, ID-family signal
  names, status outputs, storage names, generated demux names, and generated
  assertion names must remain collision-free.

This selector does not make existing `(id auto)` or transaction completion
syntax behavior-bearing by itself. The opt-in clause is required.

## Report Contract

Add an additive `response_demux` report key. The first parser/report slice
reported the contract without generated behavior in `.27`; the current
behavior-bearing `.30` shape is:

```text
response_demux:
  mode: bounded_write_bid_demux_contract
  generated_behavior: true
  write:
    response_event: axi0_write_complete
    response_id_signal: axi0_bid
    response_id_direction: generated_input
    transaction_completion_source: generated_demux
    auto_transactions: [w0, w1]
    generated_rules: [axi0_w0_response_demux, axi0_w1_response_demux]
    generated_completion_signals: [axi0_w0_complete, axi0_w1_complete]
    generated_assertions:
      - axi0_write_response_demux_active_match
      - axi0_w0_w1_write_response_demux_unique_match
  residue:
    - read_response_demux
    - same_id_ordering
    - read_data_interleaving
    - bursts
```

Historical note: `.27` reported `generated_behavior: false` and carried
`generated_write_bid_demux` as residue. `.30` shipped generated write `BID`
demux behavior and removed that residue.

## Behavior Contract Shipped By `.30`

The behavior-bearing slice uses these fixed semantics:

- declare the write response ID signal (`BID`) as a generated IAL1 input;
- treat `response-event` as the raw write response accepted event;
- match `response-event && busy && (BID == selected_id)` for each active
  auto-ID write transaction;
- generate the transaction completion signal selected by the corresponding
  transaction's `(completion NAME)` field;
- release the selected ID from the generated demux match, not from an external
  per-transaction completion input;
- assert unmatched response IDs, inactive responses, and ambiguous matches.

## Diagnostics Expected In The Parser/Report Slice

The selected parser/report implementation should reject:

- duplicate `response-demux` clauses;
- unsupported family subclauses such as `read`;
- missing `(response-event ...)`;
- duplicate `(response-event ...)`;
- response-event values that differ from top-level `write-complete` in this
  first bounded slice;
- missing or malformed `(transaction-completion generated)`;
- response-demux without `id-families`;
- response-demux without `transactions`;
- response-demux without write `auto-id-lifecycle`;
- write response-demux on a zero-width write ID family;
- write response-demux with no auto-ID write transactions.

## Residue

Still out of scope after this selector until later exact owners:

- read `RID` demux;
- read-data interleaving or reassembly;
- same-ID ordering queues;
- burst or last-beat tracking;
- address/data/control payload binding;
- repeated instances of one logical transaction;
- queued or blocking submission policy;
- full AXI manager syntax;
- `.pif`, `.ppi`, `.axi`, or other profile aliases;
- VHDL backend or VHDL rerouting behavior.
