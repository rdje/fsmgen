## Code Findings

The next residue is local to read-data coverage, not response-demux queue
generation. `_read_data_response_demux_transaction_coverage` already admits:

- one-or-more depth-2 concrete same-ID read queue-head groups for generated
  single-beat, last-beat, burst-length, runtime-validation, and multi-beat
  read-data shapes;
- exactly one depth-3 concrete same-ID read queue-head group for the selected
  single-beat, last-beat, burst-length, runtime-validation, and multi-beat
  shapes.

It still rejects multiple depth-3 groups and mixed depth-3/depth-2 groups for
read-data consumption. The response-demux side now generates those groups
after `.174`, so `.176` should audit whether the read-data coverage gate and
downstream generated data/status output rules are already group/depth driven
or need a smaller first implementation owner.

## Candidate Comparison

Read-data over multiple/mixed depth-3 groups is the next smallest
roadmap-aligned step because it composes the two just-proven surfaces:

- multiple/mixed depth-3 queue-head response-demux is now generated by `.174`;
- read-data over one depth-3 group and over multiple depth-2 groups is already
  generated for selected single-beat, last-beat, burst-length,
  runtime-validation, and multi-beat shapes.

Same-family mixed auto-ID plus concrete queue-head demux still needs explicit
allocator/queue interaction semantics. Group-local simultaneous enqueue
widening changes the admission and transition model. Packed burst-vector
outputs and alternate full-burst assembly are output-shape work beyond the
current per-transaction/per-beat bank model. Verification-output generation is
owned by the IAL1 verification-code frontier. Direct backend and
VHDL/backend-language variants remain deferred until the SystemVerilog-backed
IAL path is feature complete.

## Selected .176 Boundary

`.176` should audit generated read-data over multiple or mixed depth-3
concrete same-ID queue-head groups before any behavior change.

The audit should cover:

- read family only;
- response-demux completion source;
- generated read single-beat and read burst-last queue-head demux boundaries;
- two-depth-3 and mixed depth-3/depth-2 duplicate concrete `RID` groups;
- single-beat scalar `RDATA`/`RRESP` read-data;
- burst-last scalar last-beat read-data with no burst-length metadata,
  report-only raw-`ARLEN` metadata, and runtime-validation metadata;
- multi-beat output-bank read-data over runtime-validation metadata;
- whether the next behavior owner should start with single-beat scalar
  read-data, cover scalar single-beat plus last-beat, or cover a broader
  read-data set;
- exact future public sample names, support-accounting entries, report
  expectations, generated artifact expectations, tests, docs/book updates,
  rollback boundary, and preservation matrix.

`.176` must not enable write-family read-data, same-family mixed auto-ID plus
concrete queue-head demux, group-local simultaneous enqueue widening, packed
burst-vector outputs, alternate burst assembly, direct backend,
verification-output generation, VHDL, or another backend-language variant.
