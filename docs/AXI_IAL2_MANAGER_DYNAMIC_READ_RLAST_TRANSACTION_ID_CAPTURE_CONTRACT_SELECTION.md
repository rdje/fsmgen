# AXI IAL2 Manager Dynamic Read RLAST Transaction-ID Capture Contract Selection

Status: selector for `IAL2-FEATURE-COMPLETENESS-FRONTIER.230` on 2026-06-22.

Task-tree owner: `IAL2-FEATURE-COMPLETENESS-FRONTIER.230`

## Decision

Select `IAL2-FEATURE-COMPLETENESS-FRONTIER.231`, direct generated behavior for
bounded dynamic read burst-last/`RLAST` transaction-ID capture and response
matching.

The public contract reuses the existing explicit `response-demux.read`
burst-last syntax with exactly one transaction-local dynamic read ID. No
dynamic-only spelling, no new dynamic-ID lifecycle clause, and no metadata-first
intermediate slice are selected:

```lisp
(transactions
  (read r0
    (tag rd0)
    (request axi0_r0_request)
    (completion axi0_r0_complete)
    (id dynamic)))

(response-demux
  (read
    (response-event axi0_read_complete)
    (response-scope burst-last)
    (last-signal axi0_rlast (width 1))
    (transaction-completion generated)))
```

`(id dynamic)` remains the request-ID source contract. The matching
`response-demux.read` arm is the explicit opt-in that turns that metadata into
generated burst-last response matching. `response-event` is the raw accepted
read response beat. The generated transaction completion pulse fires only when
the raw beat's `RID` matches the captured dynamic ID and `last-signal` is
asserted.

This selector changes no parser, generator, PPIF sample, support-accounting
catalog, validation, generated artifact, test, or HDL behavior.

## Why Direct Behavior Is Next

The `.229` audit found no lower-layer prerequisite or stale report/static
cleanup blocker. The direct implementation can stay local to the AXI manager
capacity/status normalizer, report projection, generated IAL1 rules, assertion
list, support accounting, focused tests, and docs.

The grammar and public clause shape already exist because non-dynamic
`response-demux.read` supports `response-scope burst-last` and one-bit
`last-signal`. The dynamic single-beat path already proves admitted request-ID
capture, selected-ID/busy storage, generated completion, release, assertions,
and report vocabulary. `.231` should join those two already-owned surfaces.

## First Supported Boundary

The first generated dynamic read burst-last response-demux behavior is
intentionally narrow:

- exactly one read transaction in the selected read family has `(id dynamic)`;
- the selected read family has no additional read transactions;
- the selected read family has a positive-width `id-families.read` entry with
  request ID source, such as `ARID`, and response ID signal, such as `RID`;
- the dynamic read transaction has unique per-transaction request and generated
  completion events;
- the transaction completion event is generated by `response-demux.read` and is
  distinct from the raw read response event;
- `response-demux.read.response_event` equals the top-level `read-complete`
  event and is interpreted as a raw accepted read response beat;
- `response-demux.read.response_scope` is exactly `burst-last`;
- `response-demux.read.last_signal` names a generated one-bit input and is
  required with `(width 1)`;
- the selected read family has no same-family `auto-id-lifecycle.read`,
  `same-id-ordering.read`, concrete queue-head demux, mixed auto-ID/queue-head
  demux, read-data clause, burst-length clause, or runtime-validation behavior
  in this first dynamic burst-last slice.

Unrelated write-family dynamic ID metadata or generated dynamic write behavior
may remain separately governed by the existing write contract. The first public
dynamic burst-last sample should keep the shape minimal with one dynamic read
transaction and one read response-demux arm.

## Capture And Lifetime Contract

The generated capture point is the admitted dynamic read request, not the raw
request pulse alone. The capture guard remains the transaction request event
gated by the scalar read capacity acceptance expression and by the
single-active dynamic ownership bit:

```text
request_event
&& !dynamic_busy
&& (pending_reads < read_max_pending || read_completion_fanin)
```

The capture action stores the family read request-ID source into generated
selected-ID storage and sets the busy bit:

```text
dynamic_id_q   <= ARID
dynamic_busy_q <= 1
```

Matched non-last response beats do not release the busy bit and do not pulse
the transaction completion output. The busy bit remains asserted until the
generated matched last-beat completion pulse fires. The first slice does not
support a new dynamic read request while the busy bit is set, including a
same-cycle request with a matching last beat for the previous dynamic ID.

## Response Matching Contract

The generated dynamic read response-demux rule uses the existing read
response-demux match shape plus `last-signal`:

```text
response_event && dynamic_busy_q && (RID == dynamic_id_q) && RLAST
```

That rule pulses the transaction completion signal selected in the public
transaction record. Dynamic busy release is driven by that generated completion
pulse.

`response-event` is still a raw accepted read response beat, not a transaction
completion. Non-last matched beats are accepted for active-ID checking but do
not complete the transaction. Missing `RLAST`, early `RLAST`, extra beats after
`RLAST`, and `ARLEN`/beat-count consistency are not claimed by this contract.

## Assertions And Diagnostics

The generated assertion set should include at least the dynamic read checks
already selected for single-beat matching:

- an admitted dynamic read request is not accepted while the dynamic read
  transaction is already busy;
- a raw read response beat matches an active captured dynamic read ID;
- a generated dynamic read completion releases an active captured ID.

The response-active assertion is evaluated on raw read response beats and
matches only `dynamic_busy_q && RID == dynamic_id_q`; it is not gated by
`RLAST`, so a matched non-last beat remains legal and a mismatched beat remains
diagnosed.

`.231` should preserve existing diagnostics for malformed `last-signal`,
missing `last_signal_width`, non-one-bit widths, signal-name collisions,
completion/event collisions, multiple dynamic read transactions, additional
read transactions in the selected dynamic family, same-family lifecycle,
same-ID ordering, and read-data combinations.

No per-beat output, beat-valid output, beat-count assertion, missing/extra beat
assertion, or same-ID ordering assertion is selected in this first dynamic
burst-last contract.

## Report Vocabulary

The covered transaction keeps `policy: dynamic` and reports generated capture
and matching ownership once behavior ships:

```yaml
transactions:
  - name: r0
    kind: read
    id:
      policy: dynamic
      family: read
      family_width: 4
      request_id_source: axi0_arid
      response_id_signal: axi0_rid
      ownership: user_supplied
      implementation_status: generated_capture_matching
```

The `response_demux.read` report should use a dynamic burst-last mode and
artifact vocabulary:

```yaml
response_demux:
  mode: bounded_dynamic_read_rid_rlast_demux_contract
  generated_behavior: true
  read:
    mode: bounded_dynamic_read_rid_rlast_demux_contract
    generated_behavior: true
    response_event: axi0_read_complete
    response_event_role: raw_accepted_read_response_beat
    response_scope: burst_last
    response_id_signal: axi0_rid
    response_id_direction: generated_input
    last_signal: axi0_rlast
    last_signal_direction: generated_input
    last_signal_width: 1
    transaction_completion_source: generated_dynamic_demux_last_beat
    transaction_completion_semantics: matched_dynamic_id_and_last_signal
    beat_valid_output: none
    burst_length_source: rlast_only
    burst_length_validation: not_generated
    dynamic_transactions:
      - r0
    dynamic_capture:
      request_id_source: axi0_arid
      capture_event_source: admitted_dynamic_read_request
      ownership: single_active_dynamic_read
      selected_id_signal: axi0_r0_dynamic_id_q
      busy_signal: axi0_r0_dynamic_busy_q
      capture_rule: axi0_r0_dynamic_id_capture
      release_rule: axi0_r0_dynamic_id_release
    generated_rules:
      - axi0_r0_response_demux
    generated_completion_signals:
      - axi0_r0_complete
    generated_assertions:
      - axi0_r0_dynamic_request_not_busy
      - axi0_read_dynamic_response_active_match
      - axi0_r0_dynamic_completion_active
  residue:
    - same_id_ordering
    - read_data_interleaving
    - bursts
```

The single-beat dynamic read report remains unchanged and keeps
`bounded_dynamic_read_rid_demux_contract`,
`response_scope: single_beat`, and
`transaction_completion_semantics: matched_dynamic_id_single_beat`.
