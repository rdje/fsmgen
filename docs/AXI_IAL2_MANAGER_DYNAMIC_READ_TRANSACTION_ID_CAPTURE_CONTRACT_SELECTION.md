# AXI IAL2 Manager Dynamic Read Transaction-ID Capture Contract Selection

Status: selector for `IAL2-FEATURE-COMPLETENESS-FRONTIER.226` on
2026-06-22.

Task-tree owner: `IAL2-FEATURE-COMPLETENESS-FRONTIER.226`

## Decision

Select `IAL2-FEATURE-COMPLETENESS-FRONTIER.227`, direct generated behavior for
bounded single-beat dynamic read transaction-ID capture and `RID` response
matching.

The public contract reuses the existing explicit read response-demux clause
with one transaction-local dynamic read ID. No new dynamic-ID lifecycle clause
is selected:

```lisp
(transactions
  (read r0
    (tag rd0)
    (request axi0_r0_request)
    (completion axi0_r0_complete)
    (id dynamic)))

(response-demux
  (read
    (response-event axi0_read_complete)
    (response-scope single-beat)
    (transaction-completion generated)))
```

`(id dynamic)` remains the request-ID source contract. The matching
`response-demux.read` arm is the explicit opt-in that turns that metadata into
generated single-beat read response matching. The first read scope is
`single-beat`; `burst-last`, `RLAST`, read-data routing, burst-length capture,
runtime validation, and multi-beat output banks remain future owners.

This selector changes no parser, generator, PPIF sample, support-accounting
catalog, validation, generated artifact, test, or HDL behavior.

## First Supported Boundary

The first generated dynamic read response-demux behavior is intentionally
narrow:

- exactly one read transaction in the selected read family has `(id dynamic)`;
- the selected read family has no additional read transactions in the first
  generated dynamic read slice;
- the selected read family has a positive-width `id-families.read` entry with
  request ID source, such as `ARID`, and response ID signal, such as `RID`;
- the dynamic read transaction has unique per-transaction request and
  completion events;
- the transaction completion event is generated by `response-demux.read` and
  is distinct from the raw read response event;
- `response-demux.read.response_event` equals the top-level `read-complete`
  event and is interpreted as the raw accepted single-beat read response
  transfer;
- `response-demux.read.response_scope` is exactly `single-beat`;
- `response-demux.read` has no `last_signal` or `last_signal_width` fields;
- the selected read family has no same-family `auto-id-lifecycle.read`,
  `same-id-ordering.read`, concrete same-ID queue-head response-demux, mixed
  auto-ID/queue-head response-demux, read-data clause, burst-length clause, or
  runtime-validation behavior in this first generated dynamic read slice.

Unrelated write-family dynamic ID metadata or generated dynamic write behavior
may remain separately governed by the existing write contract. The first
support-accounted dynamic read behavior sample should keep the shape minimal
with one dynamic read transaction and one read response-demux arm.

## Capture Contract

The generated capture point is the admitted dynamic read request, not the raw
request pulse alone. The capture guard is the transaction request event gated
by the scalar read capacity acceptance expression and by the single-active
dynamic ownership bit:

```text
request_event
&& !dynamic_busy
&& (pending_reads < read_max_pending || read_completion_fanin)
```

The capture action stores the family read request-ID source into a generated
selected-ID register and sets the busy bit:

```text
dynamic_id_q   <= ARID
dynamic_busy_q <= 1
```

The first slice does not support a new dynamic read request while the busy bit
is set, including a same-cycle request with a matching response for the
previous dynamic ID. That preserves the single-active update-order rule
already selected for dynamic write behavior.

## Response Matching Contract

The generated read response-demux rule uses the existing read response-demux
match shape with dynamic selected-ID storage:

```text
response_event && dynamic_busy_q && (RID == dynamic_id_q)
```

The rule pulses the transaction completion signal selected in the public
transaction record. Dynamic busy release is driven by that generated
completion pulse.

The generated response event is single-beat only. It is not a burst last-beat
event, not a per-beat read-data capture event, and not a `RID`+`RLAST`
completion. Later owners must select those semantics explicitly.

## Assertions And Diagnostics

The generated assertions must cover at least:

- an admitted dynamic read request is not accepted while the dynamic read
  transaction is already busy;
- a raw read response event matches an active captured dynamic read ID;
- a generated dynamic read completion releases an active captured ID.

The first dynamic read contract has exactly one dynamic read transaction, so
multi-transaction unique-match assertions, per-ID ordering assertions,
read-data assertions, beat-count assertions, and `RLAST` assertions remain
future exact-owner work.

The `response_demux.read` report should use a dynamic-specific mode and
artifact vocabulary:

```yaml

  mode: bounded_dynamic_read_rid_demux_contract
  generated_behavior: true
  read:
    mode: bounded_dynamic_read_rid_demux_contract
    generated_behavior: true
    response_event: axi0_read_complete
    response_event_role: raw_accepted_read_response
    response_scope: single_beat
    response_id_signal: axi0_rid
    response_id_direction: generated_input
    transaction_completion_source: generated_dynamic_demux
    transaction_completion_semantics: matched_dynamic_id_single_beat
    dynamic_transactions:
      - r0
    dynamic_capture:
      request_id_source: axi0_arid
      capture_event_source: admitted_dynamic_read_request
      ownership: single_active_dynamic_read
      selected_id_signal: axi0_r0_dynamic_id_q
      busy_signal: axi0_r0_dynamic_busy_q
      capture_rule: axi0_r0_dynamic_id_capture
      release_rule: axi0_r0_dynamic_id_release
    generated_rules:
      - axi0_r0_response_demux
    generated_completion_signals:
      - axi0_r0_complete
    generated_assertions:
      - axi0_r0_dynamic_request_not_busy
      - axi0_read_dynamic_response_active_match
      - axi0_r0_dynamic_completion_active
```

The existing `dynamic_transaction_id_behavior` residue should narrow only
after behavior ships: dynamic read ID capture and single-beat `RID` matching
are covered for the single-active read shape, while burst-last dynamic read
matching, read-data routing, multiple dynamic read transactions, dynamic
same-ID ordering, queues, scoreboards, mixed dynamic/static read demux,
same-cycle recapture, direct-backend behavior, and VHDL remain residue.
