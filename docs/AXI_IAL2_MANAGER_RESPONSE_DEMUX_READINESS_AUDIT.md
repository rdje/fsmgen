## Purpose

This audit checks whether generated AXI response demux can be implemented
directly after bounded auto-ID request-ID drive, or whether a smaller contract
owner is required first.

The `.23` implementation now owns request-side IDs for explicit
`auto-id-lifecycle` families. It stores one selected ID and busy bit per
auto-ID transaction, emits first-free allocation rules, and releases the busy
bit from the transaction `completion` event. Response ID signals such as
`BID`/`RID` still remain unused for generated auto-ID completion behavior.

## Readiness Conclusion

Do **not** implement generated response demux directly yet.

Select a public contract-selection slice first. The current IAL1/IAL0/SV
substrate can likely carry a narrow bounded write-response demux once the
source contract is explicit, but the public `.ppif` surface does not yet name
the response-channel handshake event or define whether transaction
`completion` names are external inputs or generated demux outputs.

Proceed with `IAL2-FEATURE-COMPLETENESS-FRONTIER.26`: select the bounded
write-response demux public contract before parser/report or generated
behavior changes.

## Evidence

Current shipped substrate that is sufficient after contract selection:

- ID-family metadata already records write `request-id`/`response-id` signal
  names and widths.
- Bounded auto-ID lifecycle metadata already records each write transaction's
  selected-ID storage and busy storage.
- Generated IAL1 rules already use equality, conjunction, negation, output
  assignment, storage assignment, and actor-level priority edges.
- Concrete-ID assertions already prove positive-width response ID inputs can
  lower through `.isf -> .fsm -> SystemVerilog` as verification checks.
- The auto-ID first slice proves selected-ID/busy storage, allocation rules,
  release rules, and assertion carriers lower through `.fsm` and
  SystemVerilog.

Missing public contract:

- `transactions (write ... (completion NAME) ...)` currently requires a scalar
  completion name and the generator treats it as an IAL1 input.
- `write-complete` is a direction-level abstract completion event today. It is
  not explicitly a `BVALID && BREADY` response-channel event.
- The source does not say whether per-transaction completion names should be
  generated by demux or supplied by the environment.
- The source does not name unmatched-response behavior, inactive-response
  behavior, or the report key/shape for generated demux.

Silently reinterpreting existing completion fields would create contract
drift. A new exact contract owner must decide that surface first.

## Selected Boundary

The next contract selector should prefer the smallest honest demux surface:
bounded **write** response demux for explicit auto-ID lifecycle families.

Write response demux is narrower than read response demux because one `BID`
response completes one write transaction. Read response demux also needs
`RID`, `RVALID/RREADY`, `RLAST`, burst/last-beat ownership, and read-data
interleaving or reassembly policy. Those remain future exact-owner work.

The likely first generated behavior after contract selection is:

- declare the write response ID signal (`BID`) as a generated IAL1 input;
- declare or reuse an explicit write response accepted event;
- for each active auto-ID write transaction, match
  `response_event && busy && (BID == selected_id)`;
- release the transaction busy bit from the matched response;
- generate or assert the per-transaction completion signal selected by the
  public contract;
- assert unmatched `BID`, inactive response, or ambiguous match cases.

The selector may refine that shape, but it must not include read-data
interleaving, burst assembly, or full AXI manager syntax in the first demux
owner.

## Contract Questions For `.26`

The next selector must decide:

- whether to add an explicit `(response-demux ...)` clause;
- whether the first clause is write-only;
- how to name the response accepted event, for example an abstract
  `write-response`/`write-response-accepted` event or a direct event signal;
- whether transaction `completion` fields remain external, become generated
  demux output names, or are split into external and generated forms;
- whether existing `write-complete` stays as capacity-level completion fan-in
  or is reinterpreted only under an explicit opt-in clause;
- what diagnostics reject ambiguous mixed external completion and generated
  demux ownership;
- what report key records generated response-demux rules and residue.

## Generated Artifact Impact To Audit In The Implementation Slice

After the public contract is selected and parsed, the implementation slice
should prove:

- generated IAL1 declares `BID` as an input with the declared write ID width;
- generated response-demux rules are reviewable in `.isf`;
- generated `.fsm` carries the response ID width, selected-ID storage reads,
  busy releases, completion signal updates, and assertions;
- SystemVerilog declares `BID`, emits the demux/release logic, and emits the
  response-demux assertions through the existing assertion backend;
- samples without the explicit contract preserve current behavior.

## Non-Goals

This audit does not implement or select:

- parser/report implementation of response demux;
- generated response-demux rules;
- read `RID` demux or read-data reassembly;
- same-ID ordering queues;
- burst or last-beat tracking;
- address/data/control payload binding;
- repeated instances of one logical transaction;
- queued or blocking submission policy;
- full AXI manager syntax;
- `.pif`, `.ppi`, `.axi`, or other profile aliases;
- VHDL backend or VHDL rerouting behavior.
