# 0072 — An unreachable declared cap is a result, not a level to rewrite

- Date: 2026-08-19
- Type: verification architecture/scalability
- Status: selected by `HIAL-VIAL-VERIFICATION-FIXTURE-ARCHITECTURE.17.2.4.3`
- Refines: [0055](0055-vial-scale-proof-uses-orthogonal-workloads-and-stage-local-oracles.md), [0056](0056-vial-scale-measurements-use-pinned-evidence-and-bounded-failure.md), [0061](0061-vial-execution-scale-uses-a-caller-sealed-qualification-binder.md)
- Implementation owner: `HIAL-VIAL-VERIFICATION-FIXTURE-ARCHITECTURE.17.2.4.2`

## Context

Decision `0061` predicted an earliest authority for every `execution_graph_v1`
axis and level. Implementation reached all of them except the remaining
`bindings`, `execution_types`, and `source_map_records` levels, and there
measurement contradicts the prediction uniformly.

The predicted authorities were the bridge event cap at 32,768 bindings and the
VIAL 1-MiB source cap at 65,536 and 65,537 bindings and execution types, with
the 16-MiB plan cap at 262,144 and 1,000,000 source-map records. What actually
decides, every time, is the workload's own 1,114,112-byte
`MAX_SINGLE_INPUT_BYTES` construction envelope, which rejects the generated
source at `/inputs/0/content` before any product stage runs:

| Axis and level | Generated bytes | Envelope | Predicted authority |
| --- | ---: | ---: | --- |
| bindings 32,768 | 1,933,429 HIAL | 1,114,112 | bridge event cap |
| bindings 65,536 | 3,866,741 HIAL | 1,114,112 | VIAL 1-MiB source cap |
| bindings 65,537 | 3,866,800 HIAL | 1,114,112 | VIAL 1-MiB source cap |
| execution types 65,536 | 2,413,815 HIAL | 1,114,112 | VIAL 1-MiB source cap |
| execution types 65,537 | 2,413,852 HIAL | 1,114,112 | VIAL 1-MiB source cap |
| source maps 262,144 | 3,670,808 VIAL | 1,114,112 | 16-MiB plan cap |
| source maps 1,000,000 | 14,000,792 VIAL | 1,114,112 | 16-MiB plan cap |
| source maps 1,000,001 | 14,000,806 VIAL | 1,114,112 | execution source-map cap |

The total-fiber and total-operation ladders escaped the same wall by switching
to the ordinary shipped `(repeat COUNT action)` form, which reaches 65,536
fibers in 3,199 bytes and 1,000,000 operations in 4,003. That escape is not
available here: `repeat` repeats *actions*, while events, types, and endpoints
are *declarations*, and the public `.vial` and `.isf` grammars have no
declaration-repetition form. One record per unit is the only authoring shape.

The deeper fact is that these declared caps are unreachable through any shipped
route, not merely through a bigger source. `FSM::Support::VIALExecutionContract`
declares `bindings` 65,536, `execution_types` 65,536, and `source_map_records`
1,000,000, while `FSM::Support::HIALVIALBridgeContract` declares `events` 2,048,
`types` 4,096, `endpoints` 4,096, `source_map` 65,536, and a 16,777,216-byte
serialized manifest — and the execution plan carries its own 16,777,216-byte
cap. A lower cap in the layer below always wins first. Each axis's genuine
boundary was measured through the canonical route:

| Axis | Declared execution cap | Measured route boundary | Cap that decides at the boundary |
| --- | ---: | ---: | --- |
| bindings | 65,536 | accepts 2,054, rejects 2,055 | bridge `events` 2,048 at `/events` |
| execution types | 65,536 | accepts 1,043, rejects 1,044 | 16,777,216-byte serialized manifest at `/` |
| source-map records | 1,000,000 | accepts 46,294, rejects 46,295 | 16,777,216-byte serialized plan at `/plan` |

The accepted boundaries are ~32x, ~63x, and ~22x below their declared caps.

## Decision

1. **Do not re-level these axes.** The nominal `qualification_candidate_v1`,
   `limit_v1`, and `over_limit_v1` values stay exactly as decisions `0055` and
   `0061` selected them. They are the execution contract's own declared caps,
   and "this declared cap is unreachable through every shipped route" is a
   first-class result of the scale family. Rewriting the level onto the value
   that happens to work would delete the finding and leave a ladder that can
   only ever confirm itself.
2. **Do not raise the construction envelope.** It is not the real obstacle,
   only the first one: at 65,536 bindings the VIAL source is already 1,442,356
   bytes against the product's own 1,048,576-byte parser cap, and at 1,000,000
   source-map records it is 14,000,792. Raising the envelope would swap a
   fixture bound for a product bound without reaching the declared cap, while
   weakening the bounded-construction property the workload foundation exists
   to hold.
3. **Report three numbers per unreachable level, never one.** Every such level
   must record (a) the declared cap it was selected from, (b) the earliest cap
   that actually decides, with its exact diagnostic and path, and (c) the
   axis's measured route boundary — the highest value the shipped route
   genuinely reaches, and the exact cap and path that rejects one more. A level
   whose earliest decider is the construction envelope must always carry (c),
   because the envelope is a fixture bound and a fixture bound must never be
   reported as a product limit.
4. **Represent an unconstructible level explicitly.** The generator owns these
   levels, and because their sources are never admitted there is nothing to
   evaluate. `evaluate` reports `status` `envelope_unconstructible` and
   `observed_outcome` `not_constructed`, claims no SemanticIR, bridge, or plan
   identity, carries the exact `VIAL_SCALE_INPUT_ERROR` construction diagnostic,
   and records one `VIAL_SCALE_LIMIT_INTERACTION` naming the envelope plus one
   new `VIAL_SCALE_ROUTE_BOUNDARY` naming the measured boundary from clause 3.
   Both are routed to `HIAL-VIAL-VERIFICATION-FIXTURE-ARCHITECTURE.17.4`. This
   is the same shape `preflight_dominated`/`not_materialized` already uses for a
   level that is deliberately not run.
5. **Prove each route boundary through the canonical route, opt-in.** The
   boundary probes build real canonical bridges and plans, so they belong behind
   `FSMGEN_VIAL_SCALE_EXACT` under `scripts/run_with_ram_guard.sh`, not in a
   default gate. The boundary values are measurements, not selected levels, and
   must be re-measured rather than trusted if a contract limit changes.
6. **Route the cross-layer inconsistency, do not fix it here.** That
   `VIALExecutionContract` declares caps its own bridge and plan layers make
   unreachable is a real defect in the declared caps, not in the scale family.
   `.17.4` owns explicit architecture resource caps and graceful bounded
   failure, and therefore owns deciding whether the execution caps are lowered
   to what the stack can reach, the lower layers are raised, or the layering is
   documented as intentional.

## Consequences

- The `bindings`, `execution_types`, and `source_map_records` ladders can be
  authored without inventing capacity, without rewriting selected levels, and
  without reporting a fixture bound as a product limit.
- The scale family gains a second honest outcome class beside "rejected by an
  earlier product cap": "not constructible within the bounded fixture envelope,
  with the product route boundary measured separately".
- Three declared execution caps are now known to be unreachable by ~32x, ~63x,
  and ~22x, with exact evidence for `.17.4` to act on.
- No support, performance, or capacity claim changes. A measured route boundary
  is reported as measured; a declared cap that nothing reaches is reported as
  unreached.

## Containment

This decision is one bounded rationale record under the existing decision
collection limits. It changes no product behavior; implementation remains the
separate `.17.2.4.2` owner.
