## Code Findings

The `.180` implementation widened only the no-`burst_length` last-beat branch
of `_read_data_response_demux_transaction_coverage`. That branch now admits
generated read burst-last queue-head groups whose computed depths are `2` or
`3`, with at least one depth-3 group.

The adjacent report-only and runtime-assertion last-beat branches still accept
depth-2 groups and exactly one depth-3 group. The generated raw-`ARLEN`
substrate below that coverage gate is already transaction-list driven:

- one generated `axi0_arlen` input;
- per-transaction raw-`ARLEN` storage;
- per-transaction request-guarded burst-length capture rules;
- generated burst-length report fields;
- scalar last-beat read-data outputs and capture rules preserved from the
  covered read-data transaction list.

## Candidate Comparison

Report-only raw-`ARLEN` burst-length over the `.180` shape is the smallest
safe next audit:

- `.180` now proves scalar last-beat read-data over the target depth `3,3` and
  `3,2` queue sets without `burst_length` metadata;
- one-group depth-3 already followed scalar last-beat read-data with
  report-only raw-`ARLEN` before runtime validation or multi-beat output banks;
- multi-group depth-2 scalar last-beat read-data followed the same sequence;
- runtime beat-count/`RLAST` validation needs burst-length metadata first;
- multi-beat output-bank behavior needs runtime-validation metadata first.

Write-family read-data is not the next prerequisite because write responses do
not carry `RDATA` and remain a separate public-contract question. Same-family
mixed auto-ID plus concrete queue-head demux needs allocator/queue interaction
semantics. Group-local simultaneous enqueue widening changes transition
semantics. Packed burst-vector outputs and alternate full burst assembly are
output-shape work beyond the current per-transaction scalar and per-beat-bank
models. Verification-output generation is owned by the IAL1 verification-code
frontier. Direct backend and VHDL/backend-language variants remain deferred
until the SystemVerilog-backed IAL path is feature complete.

## Selected .182 Boundary

`.182` should audit generated report-only raw-`ARLEN` burst-length capture over
the generated read burst-last scalar last-beat read-data shape where every
duplicate concrete `RID` group has computed depth `2` or `3`, at least one
group has depth `3`, and the read-data capture is already generated by `.180`.

The audit should cover:

- read family only;
- `response-demux.read.response-scope burst-last`;
- one-bit `last-signal`/`RLAST`;
- generated read burst-last queue-head demux boundary
  `generated_read_burst_last_queue_head_demux`;
- `read-data.read.capture-scope last-beat`;
- `completion-source response-demux`;
- scalar `RDATA`/`RRESP` outputs;
- `read-data.read.burst-length` metadata with `source arlen`, signal width
  `8`, `encoding axlen-plus-one`, `capture request`, and `validation
  report-only`;
- two-depth-3 and mixed depth-3/depth-2 duplicate concrete `RID` groups;
- exact future public sample names, support-accounting entries, report
  expectations, generated-artifact expectations, tests, docs/book updates,
  rollback boundary, and preservation matrix.

`.182` must not enable runtime beat-count/`RLAST` validation, multi-beat
payload behavior, write-family read-data, same-family mixed auto-ID plus
concrete queue-head demux, group-local simultaneous enqueue widening, packed
burst-vector outputs, alternate burst assembly, direct backend,
verification-output generation, VHDL, or another backend-language variant.
