`IAL2-FEATURE-COMPLETENESS-FRONTIER.112`.

## Purpose

This audit follows the `.111` selector and checks whether generated AXI
read-data capture can consume generated concrete same-ID queue-head read demux
completion pulses.

The selected next owner is
`IAL2-FEATURE-COMPLETENESS-FRONTIER.113`: generated single-beat read-data
capture for the bounded read single-beat concrete same-ID queue-head demux
shape.

No parser, generator, support-accounting, sample, test, generated artifact, or
HDL behavior changes in this audit.

## Current Boundary

The existing generated read-data capture substrate is already suitable for the
first queue-head read-data behavior:

- it declares width-bearing `RDATA` and `RRESP` generated inputs;
- it declares transaction-bound generated data/status outputs;
- it emits normal guarded assignment rules, not pulse actions;
- its capture guard is the transaction completion pulse;
- the IAL1, IAL0, and SystemVerilog lowerers already carry those assignments.

The blocker is in IAL2 normalization/report ownership, not in the lowerers.
Current `read_data` normalization rejects queue-head read demux before it can
inspect the generated completion signals:

```text
read_data cannot consume concrete same-ID queue-head response_demux.read metadata
```

After that guard, the current coverage check is still auto-ID-specific:
`_normalize_read_data_read` builds the covered transaction set from
`response_demux.read.auto_transactions`. Generated queue-head read demux
instead publishes `generated_completion_signals` after behavior generation and
keeps the concrete transaction names in `same_id_issue_order_queues`.

Therefore the next implementation cannot safely be "remove the guard only".
It must make the read-data coverage source-aware for generated queue-head read
demux.

## Selected `.113` Boundary

Implement direct generated behavior for this first queue-head read-data shape:

- read family only;
- `response-demux.read.response_scope` is `single-beat`;
- the read response-demux source is generated concrete queue-head demux;
- exactly one duplicate concrete read-ID group;
- exactly two read transactions in the group;
- computed queue depth is `2`;
- `read-data.read.capture_scope` is `single-beat`;
- `read-data.read.completion_source` remains `response-demux`;
- `read-data.read.interleaving` remains `single-beat-by-rid`;
- `RDATA` and `RRESP` are generated inputs with declared widths;
- each transaction gets one generated data output, one generated status
  output, and one normal capture rule guarded by its generated queue-head
  completion pulse.

The implementation should report a queue-head-specific completion validity
such as:

```text
generated_queue_head_response_demux_completion_pulse
```

or an equivalent machine-readable field, while preserving the existing
`generated_read_response_demux_completion_pulse` report value for auto-ID
read-data samples.

The expected IAL1 rule shape is unchanged:

```lisp
(rule axi0_r0_read_data_capture axi0_r0_complete
  (axi0_r0_rdata axi0_rdata)
  (axi0_r0_rresp axi0_rresp))
```

The difference is that `axi0_r0_complete` is generated by concrete queue-head
`RID` demux rather than auto-ID selected-ID `RID` demux.

## Required Implementation Work

The `.113` slice should:

- add a support-accounted public PPIF sample that combines the `.110` read
  single-beat queue-head sample with single-beat `read-data`;
- relax the fail-closed queue-head read-data guard only for the selected
  generated read single-beat queue-head shape;
- derive read-data coverage from generated queue-head read transactions and
  generated completion signals when `response_demux.read` is queue-head based;
- keep existing auto-ID read-data behavior and report fields stable;
- add focused generator and PPIF/CLI tests for the new sample, schedule JSON,
  check JSON, semantic JSON, and `--verify-hdl`;
- prove existing auto-ID read-data and queue-head samples do not regress.

## Deferred Work

The following remain outside `.113`:

- read burst-last queue-head read-data consumption;
- last-beat or multi-beat queue-head read-data capture;
- queue groups deeper than two slots;
- multiple duplicate concrete-ID groups;
- same-family mixed auto-ID plus concrete queue-head demux;
- generalized per-ID issue-order queues;
- direct backend lowering;
- VHDL.
